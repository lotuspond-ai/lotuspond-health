Quickstart

  1. Create a LotusPond account, then open the developer console and make an organisation.
  2. Make an API key and choose what it may do. The key is shown once; keep it in your secret store.
  3. List your connections. Every organisation has a sandbox hospital with synthetic patients.
curl https://health.lotuspond.ai/v1/connections \
  -H "Authorization: Bearer lpk_…"

curl https://health.lotuspond.ai/v1/operations/patients.search \
  -H "Authorization: Bearer lpk_…" -H "Content-Type: application/json" \
  -d '{"connection": "<connection id>", "name": "asha"}'

Every answer is JSON: {"status": "done", "result": …} with a FHIR R4 resource or Bundle, or 202 with {"status": "pending_approval", "approval": …} for a write that waits for a clinician. Errors carry a code and a plain message.

MCP server

Give your own agents the same operations as tools. Point any MCP client that supports Streamable HTTP at the organisation endpoint and send your key as a bearer token:

{
  "mcpServers": {
    "lotuspond-hospitals": {
      "type": "http",
      "url": "https://health.lotuspond.ai/v1/mcp",
      "headers": { "Authorization": "Bearer lpk_…" }
    }
  }
}

The tools follow the key: list_connections, search_patients, list_encounters, upload_document, get_claim_status and get_approval. A key without an operation does not see its tool. This server is for organisations; people connect their own records at /mcp instead.

Going live with a hospital

New organisations reach only the sandbox. To reach a real hospital system, ask for live access in the console and tell us which hospital and which system. Before we add the connection we need:

  • The hospital’s written authority for your organisation to read or write the records you named.
  • A service account or token from the hospital’s IT team, and the interface switched on (FHIR R4 for TrakCare, Bahmni and other FHIR systems). For an Eka Care clinic: a sharing key for its Eka workspace.
  • A data-processing agreement between your organisation and LotusPond.

We never sign in as a hospital’s staff, never work around multi-factor sign-in or a vendor’s access controls, and never use a system against its vendor’s terms.

Safety and records

  • Writes wait for a clinician. An upload is held, with its content encrypted, until someone with approval rights in your organisation approves it in the console. Then it is sent and the held copy is deleted.
  • Every call is recorded. Each key lists what it may do; every call, allowed or refused, is logged with its outcome and shown in the console.
  • Credentials are sealed. Hospital credentials are encrypted at rest and never returned by the API.
  • Data in India. The organisation API runs on servers in India.
